# Two enhanced installations with the node wrapper

Inspection at PR5144 head 8b636936a353bef384ae61b6351f63adc0c007fd found a per-copy FederationModulesPlugin hook map combined with EmbedFederationRuntimePlugin deduplication by a shared compiler tap name. This standalone investigation changes no production ownership design and grants no merge sign-off.

Build enhanced and node with `pnpm exec turbo run build --filter=@module-federation/enhanced... --filter=@module-federation/node`. Then run `node tools/repros/enhanced-node-copies.cjs`. An optional `MF_REPRO_BUILD_ROOT` points at an already built checkout. The script copies both installed package trees, places enhanced copy B in the node wrapper's own node_modules, uses a temporary fixture, and runs each scenario in a fresh process. It prints structured JSON and removes its fixture. An aggregate strict gate exits nonzero unless every scenario has successful remote execution and runtime marker assertions and no compiler, harness, thrown, or execution errors. Compiler close errors are propagated.

The app applies the real enhanced ModuleFederationPlugin. The node side applies the real NodeFederationPlugin with useRuntimePlugin:true, resolving its own enhanced dependency. Both provide the same complete HTTP remote map, use remoteType:script, commonjs-module containers, async-node target, distinct shared providers, and a beforeInit runtime marker. The local server supplies CommonJS containers; no container globals are preinstalled. Assertions require both HTTP requests and the actual remote values plus shared values. The first runtime marker is checked against same-copy controls, rather than assuming two runtimes should initialize.

All six execution checks passed on Node 24.15.0 and webpack 5.104.1: mixed app→node and node→app, the same-copy equivalent in both orders, and each wrapper on its own compiler. Each fetched /app.js and /node.js and returned [app-dep, node-dep, app-remote, node-remote]. Results are recorded in the adjacent JSON excerpt. Conflicting FEDERATION_BUILD_IDENTIFIER warnings occur in both mixed-copy and same-copy compositions; they are explicitly recorded and are not attributed to duplicate installations.

Mixed copies have separate compilation hook objects, one compiler embed tap, and two constructor-keyed FederationRuntimeDependency factories. Only the first copy's hook map has the embed subscriber. Module-local onceForCompiler WeakSets independently run prependEntry/injectRuntime for each copy. Federation runtime requirements and embed taps select the first runtime. Same-copy controls have one factory and likewise initialize the first runtime. Separate constructor keys are registered against the same normalModuleFactory, so this fixture finds no missing factory or template.

A preliminary disjoint-remote-map experiment failed RUNTIME-004 for the second plugin's remote in both mixed-copy and same-copy controls. Manifest-enabled variants also failed in ModuleHandler._handleRemoteModule reading undefined options.alias, across both copy arrangements. Neither establishes a duplicate-install regression. The committed fixture keeps manifest:false and supplies coherent maps to test actual remote execution. It does not establish support for combining independent federation configurations or heterogeneous enhanced versions.

The wrappers accept this composition without a duplicate-copy diagnostic; they do not promise configuration merging. These results support the tested coherent configuration, not unrestricted same-compiler ownership safety. If independent configurations are intended to work, review a compiler-scoped owner with explicit version compatibility and configuration semantics as separate architecture work. If that composition is unsupported, define and document its boundary before adding a fail-fast diagnostic. Do not blindly globalize WeakMaps or suppress serializer errors. Keep PR5144 sign-off on hold pending independent architectural review.
