# Chrome Devtool

The `Micro-frontend` architecture differs from the traditional monolithic application development model. Its characteristics of separate development, deployment, and debugging require a new set of debugging tools to meet new usage scenarios. For example: how to verify the effect of modules in actual projects during development, whether a producer's dependencies are reused with the host environment, which modules are loaded on the current page, and what the dependency relationships and data flow between modules look like.

`Chrome Devtool` provides the following capabilities:

- Supports proxying remote modules from an online page to a local one.
- Switch online remote module versions for quick functional verification.
- Support viewing module dependency information.
- Support filtering specified module dependency information.
- Support Loading Trace for remote, shared, component-ready signals, and failure reports.

::: tip Limitations of Chrome Devtool

You must use `mf-manifest.json` to use the visualization and proxy capabilities provided by `Chrome devtool`.

:::

::: tip Debugging with an AI coding agent

Use [Divebell](/guide/debug/divebell.html) when an agent needs structured
evidence for an MF runtime failure, loading chain, or performance bottleneck.

:::

## Choose an extension variant

Module Federation Devtools provides two interface variants and supports **WebMCP**, allowing an AI agent to call debugging tools registered on the page.

| Scenario                                                                                                                   | Variant                  | Interface                                                |
| -------------------------------------------------------------------------------------------------------------------------- | ------------------------ | -------------------------------------------------------- |
| Desktop Chrome with side panel or developer tools support                                                                  | Chrome (`dist/chrome`)   | Extension side panel or Module Federation DevTools panel |
| An AI application's embedded browser that supports Chrome extensions but not side panels, such as Codex's embedded browser | Browser (`dist/browser`) | Compact popup opened from the extension icon             |

Both variants retain the same implemented debugging features: **module proxying and version switching, module information, dependency graphs, shared dependencies, React HMR / Fast Refresh, Loading Trace, and report export**. The Browser variant adapts the entry point and layout without removing these features. Both include WebMCP.

Compatibility with GPT and other AI applications depends on the embedded browser supporting extension loading and the required extension APIs. Agent access also requires a host that supports WebMCP registration, discovery, and invocation. Tool discovery and a read-only state call have been verified in Codex's embedded browser; this does not imply support in every AI browser. Hosts without WebMCP can still use the extension UI.

### Download and install the Browser variant

1. Open [Module Federation Releases](https://github.com/module-federation/core/releases), choose a stable release containing a Browser extension asset, and download its Browser ZIP from the release notes or **Assets**. Browser ZIPs are published with `latest` releases; `next` previews do not create GitHub Releases or assets. Do not download GitHub's automatically generated **Source code** archives.
2. Extract the ZIP and use the target embedded browser's extension manager to load the directory containing `manifest.json`. Installing the extension in desktop Chrome does not install it in an embedded browser.
3. Open or refresh the target page, then click the extension icon. After an update, reload the extension and refresh existing pages.

If a release does not yet include a Browser asset, run `pnpm --filter @module-federation/devtools run build:devtool` in the repository and load `packages/chrome-devtools/dist/browser`. Enable only one MF extension variant per browser to avoid duplicate injection. See below for Chrome Web Store installation; new feature availability depends on the published store version.

### Work with an agent through WebMCP

The extension registers tools automatically at page startup. The popup can remain closed, and the application does not need an additional WebMCP SDK.

| Tool                              | Purpose                                                          |
| --------------------------------- | ---------------------------------------------------------------- |
| `mf_get_state`                    | Runtime state, proxy/HMR configuration, and loading reports      |
| `mf_get_modules`                  | All modules or a specific module                                 |
| `mf_get_dependencies`             | Module dependency data                                           |
| `mf_get_shared`                   | Shared dependency versions and loading state                     |
| `mf_set_proxy` / `mf_clear_proxy` | Configure or clear module proxies                                |
| `mf_set_hmr`                      | Enable or disable development React replacement and Fast Refresh |
| `mf_configure_loading_trace`      | Configure Loading Trace                                          |
| `mf_get_loading_reports`          | Read loading reports                                             |
| `mf_export_snapshot`              | Export a diagnostic JSON snapshot                                |

For example, ask a WebMCP-capable agent:

```text
Read the current MF state and preserve existing proxy rules.
Proxy mf_playground to https://localhost:3006/mf-manifest.json,
enable HMR, save, reload the page, and verify the configuration.
```

`mf_set_proxy` replaces the complete rule list, so read the existing state before editing. Configuration tools save settings and return `reloadRequired`; the agent reloads after receiving the response. Startup scripts apply settings before application React loads. With HMR enabled, all React 19.x versions use the React and ReactDOM **development** bundles from `umd-react@19.2.4`; `react-dom/client` reuses the same ReactDOM instance.

WebMCP covers implemented runtime debugging capabilities. Graph layout, filtering, theme, and language remain UI controls. Agents receive structured dependency data, and export tools return JSON. The Performance panel is currently a placeholder, not an implemented performance analysis feature.

::: tip Tools are not discovered

Reload the extension and refresh the page, then inspect `window.__MF_DEVTOOLS_WEBMCP__` in the page console. `registered` means registration succeeded; `unavailable` means no usable host API appeared within 30 seconds; `error` includes an error message. Registration supports `document.modelContext` or `navigator.modelContext` with `registerTool`; `unregisterTool` is optional. After registration, the agent must discover tools through the host.

:::

::: warning Proxy and configuration boundaries

The extension does not bypass CSP, CORS, or browser network restrictions. Proxying an HTTPS page to a local HTTP server still requires compatible page policies, protocols, and server CORS headers. WebMCP and the UI share page settings stored in the origin's localStorage. Same-origin tabs may share settings; do not rely on them to keep conflicting configurations separate.

:::

## Usage Scenarios

DevTools provides multiple functional panels suitable for different debugging needs in development and production environments:

- **Proxy**: Used to proxy modules from online or test environments to the local development environment.
  - Supports local service port numbers, e.g., key: appA -> value: `http://localhost:3000/mf-manifest.json`, the page will directly load `Module Federation` content from port 3000.
  - Supports using `mf-manifest.json` file address format, e.g., key: appA -> value: `https://xxx/static/mf-manifest.json`, the page will directly load `Module Federation` content from the specified address.

- **Module Info**: Used to view detailed information of all Federation modules loaded on the current page, including version, entry address, etc.

- **Dependency Graph**: Visually displays the dependency reference relationships between modules, helping to clarify complex micro-frontend architectures.

- **Shared**: In-depth analysis of Shared Dependencies usage.
  - View loaded and unloaded shared dependencies.
  - Analyze version reuse of shared dependencies (Loaded / Reused).
  - Check the effective status of configurations such as Singleton and Strict Version.

- **Loading Trace**: Records Module Federation loading on the current page.
  - Inspect `loadRemote` and `loadShare` start, success, failure, and recovery states.
  - See which consumer loaded which remote and expose, and which shared provider/version was selected.
  - If the page already uses the [Observability Plugin](/plugin/plugins/observability-plugin.html), the panel reads those reports and shows `CUSTOM`.
  - If the page does not use the plugin, click `Observe now` to temporarily inject the Chrome collection plugin for the current tab.

## Overall Interaction

As shown below, the proxy page provides options such as `add new proxy module`, `producer selector`, `version or local port or custom entry`, etc.

- Select a module that the target page needs to proxy by selecting `producer selector`;
- Select or enter the specified address (including port number and address ending with `mf-manifest.json`) through `version or local port` for proxy operation;
- If you need to proxy multiple modules at the same time, click the `add new proxy module` area to add the corresponding proxy module.
- **Current-tab inspection**: The panel reads the target tab’s runtime and module information. Settings are stored in the page origin’s localStorage and may be shared by same-origin tabs.

## Loading Trace

The `Loading Trace` tab answers what actually happened during Module Federation loading. Use it when the page is blank, a component stays in loading, shared versions are unclear, or a producer fails intermittently.

![](https://module-federation-assest.netlify.app/document/guide/chrome-devtools/loading-trace-overview-en.png)

The top status means:

- `OFF`: no readable loading report has been found on the current page.
- `ON`: Chrome collection is enabled for the current tab.
- `CUSTOM`: the inspected page already registered its own observability plugin, and DevTools is reading those reports.

Common workflow:

1. Open the target page.
2. Open Chrome DevTools and choose the `Module Federation` panel.
3. Open `Loading Trace`.
4. If the status is `OFF`, click `Observe now`. The page reloads once.
5. Reproduce the issue or trigger the remote component load you want to inspect.
6. Select a report and inspect current loading, previous loading records, the event timeline, and troubleshooting suggestions.
7. Click `Export` to save the full report.

Report states:

- `Success`: the MF chain completed. Remote reports show the remote result; shared reports show the selected provider and version.
- `Failed`: the chain failed. Start from the failed phase, error code, and suggested actions.
- `Pending`: a start event was recorded, but no completion, failure, or recovery event was seen yet.
- `Recovered`: loading hit a problem first, then continued through fallback or recovery.
- `Basic observability`: the runtime version is too low or cannot be detected, so detailed phases may be missing.

### Analyze an exported report

The exported JSON contains `config`, `scopes`, and `reports`. For each report, start with:

![](https://module-federation-assest.netlify.app/document/guide/chrome-devtools/loading-trace-shared-report-en.png)

- `diagnosis`: the troubleshooting conclusion, facts, and next actions.
- `summary`: the final state, such as `runtime-loaded`, `component-loaded`, `shared-resolved`, `failed`, `recovered`, or `pending`.
- `remote` / `shared`: what was loaded. For shared reports, inspect provider, required version, selected version, and available versions.
- `loadedBefore`: whether the same producer had already been loaded by another consumer.
- `events`: the ordered timeline, useful for finding the phase that got stuck.

You can give the exported report directly to an AI coding agent:

```text
/mf obs

I have an MF Loading Trace report exported from Chrome DevTools.
Please tell me whether the load succeeded, where it failed, who likely owns the issue, and how to fix it.

<paste the exported JSON>
```

## FAQ

### Does it support multi-tab isolation debugging?

Runtime inspection targets a tab, but proxy, HMR, and Loading Trace settings are stored in the page origin’s localStorage. Same-origin tabs may share settings and read the same configuration after reload. Use separate origins or browser profiles for conflicting configurations.

### When does the configuration take effect?

- ✅ Matches verification rules
- ✅ Configuration rule is checked
- ✅ Configuration filled in correctly, page displays: Proxy configuration has taken effect, remote module obtained successfully, corresponding page has been automatically refreshed.

### Partial configuration matches rules

The plugin will filter out **modules that match the configuration rules** for proxying.
