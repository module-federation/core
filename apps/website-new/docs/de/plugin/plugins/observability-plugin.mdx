# Observability-Plugin {#observability-plugin}

Das Observability-Plugin macht Ladevorgänge von Module Federation nachvollziehbar. Es zeichnet Ladeereignisse zur Laufzeit auf, fasst das Ergebnis zusammen, gibt bei Ladefehlern eine stabile `traceId` aus und kann Runtime-Fehler mit Build-Informationen verknüpfen.

Das Plugin ist für Module Federation ab `2.5.0` vorgesehen. In älteren MF-Versionen helfen Runtime-Fehlercodes weiterhin bei der grundlegenden Fehlersuche. Für die ausführlicheren Berichte und die Beobachtung der Ladevorgänge musst du jedoch auf `2.5.0+` aktualisieren und dieses Plugin aktivieren.

Verwende es, wenn du beispielsweise folgende Fragen beantworten möchtest:

- Wurde dieses Remote erfolgreich geladen?
- Welche Phase ist fehlgeschlagen: manifest, remoteEntry, init, expose, factory oder shared?
- Konnte der Ladevorgang über einen Runtime-Fallback oder einen Wiederherstellungspfad fortgesetzt werden?
- Welcher Provider und welche Version einer Shared-Abhängigkeit wurden ausgewählt?
- Hat `preloadRemote` seine Ressourcen tatsächlich vollständig geladen?
- Welchen Bericht sollte ich einer Person oder einem KI-Coding-Agenten geben?

Die Beobachtung von Shared-Abhängigkeiten ist auf die MF-Instanz begrenzt. Sie zeigt, welche MF-Instanz eine Shared-Abhängigkeit geladen hat, welcher registrierte Provider und welche Version ausgewählt wurden sowie die zugehörige Scope-, Versions- und Eager-Konfiguration. Eine ursächliche Verbindung von dieser Shared-Abhängigkeit zu einem bestimmten Remote oder Expose ist damit nicht garantiert. Wenn ein Ablauf mehrere Shared-Abhängigkeiten umfasst, prüfe alle Ereignisse mit `phase: "shared"`. `summary.shared` enthält nur die zuletzt beobachtete Shared-Zusammenfassung.

Wenn das Build-Plugin `customShareInfo` bereitstellt, aber kein registrierter Shared-Provider dazu passt, ist das nicht immer ein fataler Fehler. Im Bericht erscheint der behandelte Pfad als `summary.outcome: "recovered"`, `summary.phases.shared.status: "complete"` und `shared.reason: "custom-share-info-unmatched"`. Das bedeutet, dass die Runtime den Ablauf über einen wiederherstellbaren Pfad fortgesetzt hat. Prüfe die Shared-Konfiguration nur dann, wenn du die Auswahl eines bestimmten Providers oder einer bestimmten Version erwartet hast.

Die Preload-Beobachtung zeigt, ob `preloadRemote` seine Ressourcen tatsächlich vollständig geladen hat. Nach Abschluss von `preloadRemote` enthalten Berichte Ressourcenergebnisse mit `phase: "preload"`, Ressourcen-URL, Ressourcentyp, Status und Preload-`id`. Der Status kann `success`, `error`, `timeout` oder `cached` sein. Wenn der Aufruf keine `exposes` angibt, lautet die `id` `remoteName/*`. Sind `exposes` angegeben, wird jedes Expose separat als `remoteName/expose` erfasst.

Wenn du den Ablauf mit Berichten zunächst ausprobieren oder Berichte direkt auf der Seite prüfen und exportieren möchtest, installiere die aktuelle [Module-Federation-Erweiterung für Chrome](https://chromewebstore.google.com/detail/module-federation/aeoilchhomapofiopejjlecddfldpeom). Der Tab `Loading Trace` liest Berichte aus dem Observability-Plugin der Seite. Falls die Seite das Plugin nicht installiert hat, kann die Erweiterung auch eine vorübergehende Erfassung für den aktuellen Tab starten. Den vollständigen Ablauf findest du unter [Chrome Devtool Loading Trace](/guide/debug/chrome-devtool.html#loading-trace).

## Installation {#install}

```bash
npm install @module-federation/observability-plugin
```

## Browser-Runtime {#browser-runtime}

Verwende im Runtime-Code für den Browser den Standardeinstiegspunkt.

```ts title="mf-runtime.ts"
import { createInstance } from '@module-federation/runtime';
import { ObservabilityPlugin } from '@module-federation/observability-plugin';

export const mf = createInstance({
  name: 'runtime_host',
  remotes: [
    {
      name: 'remote1',
      entry: 'https://example.com/mf-manifest.json',
    },
  ],
  plugins: [
    ObservabilityPlugin({
      level: 'verbose',
      browser: {
        enabled: true,
        scope: 'runtime_host',
      },
    }),
  ],
});
```

Wenn ein Module-Federation-Ladevorgang fehlschlägt, gibt das Plugin einen kompakten Hinweis über `console.error` aus:

```text
[Module Federation] Observability report generated
traceId: mf-...
phase: manifest
errorCode: RUNTIME-003
read: window.__FEDERATION__.__OBSERVABILITY__["runtime_host"].getReport("mf-...")
```

Führe den Befehl `read:` in der Browserkonsole aus, um den vollständigen Bericht zu erhalten.

Du kannst Berichte auch direkt lesen:

```ts
window.__FEDERATION__.__OBSERVABILITY__.runtime_host.getLatestReport();
window.__FEDERATION__.__OBSERVABILITY__.runtime_host.getReport('mf-...');
window.__FEDERATION__.__OBSERVABILITY__.runtime_host.getReports({ limit: 5 });
window.__FEDERATION__.__OBSERVABILITY__.runtime_host.findReports({
  remote: 'remote1',
});
window.__FEDERATION__.__OBSERVABILITY__.runtime_host.exportReport('mf-...');
window.__FEDERATION__.__OBSERVABILITY__.runtime_host.getRuntimeState();
```

Wenn du Ladeabläufe während der Entwicklung beobachten möchtest oder die Seite im Ladezustand bleibt, ohne einen Fehler auszugeben, aktiviere den Browser-Reader. Im Browser-Entwicklungsmodus werden Startmeldungen standardmäßig ausgegeben:

```ts
ObservabilityPlugin({
  level: 'verbose',
  browser: {
    enabled: true,
    scope: 'runtime_host',
  },
});
```

Das Plugin gibt `console.info` nur beim Start von `loadRemote` oder `loadShare` aus. Die Zeile enthält die `traceId` und den Lesebefehl. Agenten können mit dieser `traceId` den aktuellen Bericht einschließlich `status: "pending"`, `summary.phases`, `updatedAt` und `duration` prüfen. Mit `trace.printStart: false` deaktivierst du die Ausgabe im Browser-Entwicklungsmodus. Im Browser-Produktionsmodus sind Startmeldungen standardmäßig deaktiviert und benötigen `trace.printStart: true`.

## Runtime im Produktionseinsatz {#production-runtime}

Stelle im Produktionseinsatz standardmäßig keinen öffentlichen Browser-Reader bereit. Halte die Konsolenausgabe klein und lade Berichte über dein eigenes System hoch.

```ts title="mf-runtime.ts"
import { ObservabilityPlugin } from '@module-federation/observability-plugin';

export const observabilityPlugin = ObservabilityPlugin({
  level: 'summary',
  browser: {
    mode: 'production',
  },
  onReport(report) {
    if (report.status === 'error' || report.summary.outcome === 'recovered') {
      navigator.sendBeacon(
        '/api/mf-observability',
        JSON.stringify({
          traceId: report.traceId,
          status: report.status,
          diagnosis: report.diagnosis,
          summary: report.summary,
          remote: report.remote,
          shared: report.shared,
          moduleInfo: report.moduleInfo,
        }),
      );
    }
  },
});
```

Im Browser-Produktionsmodus enthält der Konsolenhinweis nur `traceId` und einen bekannten `errorCode`. Der vollständige Bericht sollte über `onReport`, `exportReport()` oder dein eigenes Telemetrie-Backend bereitgestellt werden.

## Berichte aus `onReport` analysieren {#analyze-reports-from-onreport}

`onReport` wird bei jeder Aktualisierung eines Berichts aufgerufen. Produktionsanwendungen müssen normalerweise nicht jeden erfolgreichen Bericht speichern. Der Callback eignet sich jedoch, um Fehler, wiederhergestellte Abläufe oder ausgewählte erfolgreiche Ladeabläufe an dein eigenes System zu übertragen.

Übliche Strategien:

- Nur Fehlersuche: Berichte mit `report.status === "error"` und `report.summary.outcome === "recovered"` hochladen.
- Shared-Abhängigkeiten prüfen: Zusätzlich `report.summary.outcome === "shared-resolved"` hochladen, um den ausgewählten Provider und die Version zu sehen.
- Preload-Ergebnisse prüfen: Zusätzlich `report.summary.outcome === "preloaded"` oder fehlgeschlagene Ereignisse mit `phase: "preload"` hochladen, um erfolgreiche, fehlgeschlagene, abgelaufene und gecachte Preload-Ressourcen zu zählen.
- Ladevorgänge umfassend beobachten: Erfolgreiche Berichte mit `runtime-loaded`, `component-loaded` und `shared-resolved` stichprobenartig erfassen.

Lies einen Bericht in dieser Reihenfolge:

1. `diagnosis`: Hinweis auf den zuständigen Bereich, wichtige Fakten und vorgeschlagene nächste Schritte.
2. `summary`: Endergebnis. `runtime-loaded` bedeutet, dass das Remote geladen wurde. `component-loaded` bedeutet, dass der Anwendungscode Bereitschaft gemeldet hat. `shared-resolved` bedeutet, dass ein Shared-Provider und eine Version ausgewählt wurden. `preloaded` bedeutet, dass das Vorabladen der Ressourcen abgeschlossen ist. `failed` bedeutet, dass das Laden fehlgeschlagen ist. `recovered` bedeutet, dass die Runtime einen wiederherstellbaren Pfad verwendet hat.
3. `remote` / `shared`: aktuelles Ladeziel. Prüfe bei Shared-Berichten `provider`, `requiredVersion`, `selectedVersion` und `availableVersions`.
4. `moduleInfo`: vom Deployment bereitgestellte Modulinformationen, hilfreich bei Problemen mit der Snapshot-Zuordnung.
5. `events`: chronologische Ereignisfolge, hilfreich zum Auffinden der Phase, in der der Ablauf hängen geblieben ist.

Beispiel:

```ts
ObservabilityPlugin({
  level: 'summary',
  browser: {
    mode: 'production',
  },
  onReport(report) {
    const outcome = report.summary.outcome;
    const shouldUpload =
      report.status === 'error' ||
      outcome === 'recovered' ||
      outcome === 'shared-resolved' ||
      outcome === 'preloaded';

    if (!shouldUpload) {
      return;
    }

    navigator.sendBeacon(
      '/api/mf-observability',
      JSON.stringify({
        traceId: report.traceId,
        status: report.status,
        outcome,
        diagnosis: report.diagnosis,
        summary: report.summary,
        remote: report.remote,
        shared: report.shared,
        moduleInfo: report.moduleInfo,
        events: report.events,
      }),
    );
  },
});
```

Du kannst den hochgeladenen Bericht einem KI-Coding-Agenten geben:

```text

Hier ist ein aus der Produktion hochgeladener MF-Observability-Bericht.
Bitte sag mir, ob der Ladevorgang erfolgreich war, wo er fehlgeschlagen ist, wer das Problem wahrscheinlich verantwortet und wie es behoben wird.
```

## Runtime-Optionen {#runtime-options}

`ObservabilityPlugin(options)` unterstützt diese Runtime-Optionen:

| Option | Typ | Standard | Beschreibung |
| --- | --- | --- | --- |
| `enabled` | `boolean` | `true` | Aktiviert oder deaktiviert das Plugin. Deaktivierte Plugins zeichnen keine Ereignisse auf und erzeugen keine Berichte. |
| `level` | `'summary' \| 'verbose'` | `'summary'` | Detailgrad der Berichte. `verbose` behält die vollständige Ereignisfolge bei. |
| `maxEvents` | `number` | integriertes Limit | Maximale Anzahl aufbewahrter Ereignisse pro Plugin-Instanz. |
| `console` | `boolean` | `true` | Gibt bei einem Ladefehler einen kurzen Hinweis über `console.error` aus. |
| `printRawStack` | `boolean` | `false` | Gibt den ursprünglichen Fehler-Stack in der Konsole aus. Im Produktionseinsatz standardmäßig deaktiviert lassen. |
| `stackTrace.enabled` | `boolean` | `true` | Speichert einen gekürzten Stack im Bericht. |
| `stackTrace.maxLines` | `number` | integriertes Limit | Maximale Anzahl der Stack-Zeilen im Bericht. |
| `stackTrace.maxLength` | `number` | integriertes Limit | Maximale Anzahl der Stack-Zeichen im Bericht. |
| `collector` | `boolean \| { enabled?: boolean; port?: number }` | `false` | Sendet Browser-Runtime-Ereignisse per POST an einen lokalen Collector. `true` verwendet `127.0.0.1:17891`; eine eigene Konfiguration benötigt nur `port`. Das dient lokalem KI-Debugging. Das Runtime-Plugin startet den Server nicht selbst. |
| `browser.enabled` | `boolean` | `false` | Stellt den Browser-Reader unter `window.__FEDERATION__.__OBSERVABILITY__` bereit. |
| `browser.scope` | `string` | Host-Name | Namespace des Browser-Readers, zum Beispiel `runtime_host`. |
| `browser.mode` | `'development' \| 'production'` | `'development'` | Ausgabemodus im Browser. Der Produktionsmodus hält Konsolenhinweise klein. |
| `trace.printStart` | `boolean` | `true` im Browser-Entwicklungsmodus, `false` im Browser-Produktionsmodus | Gibt beim Start von `loadRemote` oder `loadShare` eine Meldung über `console.info` aus, damit Entwicklungsagenten die `traceId` erhalten. Der Produktionsmodus erfordert ausdrücklich `true`. |
| `react.enabled` | `boolean` | `true` | Hauptschalter für React-spezifische Debugging-Optionen. Mit `false` wird jegliches Wrapping für React deaktiviert. |
| `react.injectLoadedCallback` | `boolean` | `false` | Umschließt passende Remote-React-Komponenten ausdrücklich mit einem Wrapper und fügt `onMFRemoteLoaded` ein. Das ändert die Komponentenreferenz. Verwende es als vorübergehende Debugging-Option und entferne es nach der Fehlerbehebung. |
| `react.remoteIds` | `string[]` | `[]` | Beschränkt das Einfügen des Callbacks auf bestimmte Remote-Anfragen wie `remote/Button` oder `./Button`. Ein leeres Array bedeutet keine Remote-Filterung. |
| `react.defaultExportMode` | `'preserve' \| 'component'` | automatisch | Steuert, ob Remotes mit `{ default: Component }` direkt die umschlossene Komponente zurückgeben. Behalte normalerweise den Standardwert bei. |
| `onEvent` | `(event, report, context) => void` | `undefined` | Wird aufgerufen, wenn ein Observability-Ereignis erfasst wird. |
| `onReport` | `(report, context) => void` | `undefined` | Wird bei jeder Berichtsaktualisierung aufgerufen. Produktionsanwendungen laden hier häufig Berichte hoch. |
| `onRawError` | `(error, context) => void` | `undefined` | Wird mit dem ursprünglichen Fehlerobjekt aufgerufen, um dein eigenes Fehlersystem anzubinden. |

## Node- oder SSR-Runtime {#node-or-ssr-runtime}

Verwende den Node-Einstiegspunkt, wenn du lokale Berichtsdateien brauchst.

```ts title="mf-node-runtime.ts"
import { createInstance } from '@module-federation/runtime';
import { ObservabilityPlugin } from '@module-federation/observability-plugin/node';

createInstance({
  name: 'node_host',
  remotes: [],
  plugins: [
    ObservabilityPlugin({
      level: 'verbose',
      fileOutput: true,
      directory: '.mf/observability',
    }),
  ],
});
```

Der Node-Einstiegspunkt schreibt:

- `.mf/observability/latest.json`: letzter vollständiger Bericht
- `.mf/observability/events.jsonl`: Ereignisstrom für mehrere Traces

Lies zuerst `latest.json`. Verwende `events.jsonl` nur, wenn du die zeitliche Reihenfolge oder mehrere Traces brauchst.

## Build-Observability {#build-observability}

Füge das Build-Plugin neben deinem Module-Federation-Build-Plugin hinzu, wenn du separate Informationen aus dem Build benötigst.

```js title="webpack.config.js"
const {
  ModuleFederationPlugin,
} = require('@module-federation/enhanced/webpack');
const {
  ObservabilityBuildPlugin,
} = require('@module-federation/observability-plugin/build');

const moduleFederationOptions = {
  name: 'runtime_host',
  remotes: {
    remote1: 'remote1@https://example.com/mf-manifest.json',
  },
  exposes: {
    './Button': './src/Button',
  },
  shared: {
    react: { singleton: true, requiredVersion: '^18.0.0' },
  },
};

module.exports = {
  plugins: [
    new ModuleFederationPlugin(moduleFederationOptions),
    new ObservabilityBuildPlugin({
      moduleFederation: moduleFederationOptions,
    }),
  ],
};
```

Build-Observability kann folgende Dateien schreiben:

- `.mf/observability/build-info.json`
- `.mf/observability/build-report.json`

Runtime-Berichte betten diese Dateien nicht ein. Wenn du für die Fehlersuche Build-Informationen benötigst, lies die Build-Datei separat und vergleiche sie mit dem Runtime-Bericht.

## Erfolgreichen Abschluss der Anwendungslogik melden {#mark-business-success}

Module Federation kann erkennen, dass ein Remote-Modul geladen wurde. Es kann aber nicht immer erkennen, ob deine Anwendungskomponente ihren Datenabruf, das Rendern eines Diagramms oder die SDK-Initialisierung abgeschlossen hat.

Wenn `react.injectLoadedCallback` ausdrücklich aktiviert ist, fügt das Plugin passenden Remote-React-Komponenten eine Prop `onMFRemoteLoaded` hinzu. Der Provider kann sie aufrufen, sobald seine eigene Bereitschaftsbedingung erfüllt ist:

```tsx
import { useEffect } from 'react';
import type { OnMFRemoteLoaded } from '@module-federation/observability-plugin';

export default function RemotePanel({
  onMFRemoteLoaded,
}: {
  onMFRemoteLoaded?: OnMFRemoteLoaded;
}) {
  useEffect(() => {
    onMFRemoteLoaded?.({
      metadata: {
        dataReady: true,
      },
    });
  }, [onMFRemoteLoaded]);

  return <section>Remote panel</section>;
}
```

Bei Bedarf kann der Consumer-Code weiterhin direkt die Instanzmethode aufrufen:

```ts
import { getInstance } from '@module-federation/runtime';
import '@module-federation/observability-plugin';

getInstance()?.markComponentLoaded({
  requestId: 'remote1/Button',
  componentName: 'Button',
  metadata: {
    route: '/dashboard',
  },
});
```

Der Bericht enthält dann `component:business-loaded` und `summary.outcome: "component-loaded"`.

## React-Callback für den Ladeabschluss einfügen {#inject-react-loaded-callback}

Für die Entwicklung, KI-Debugging oder vorübergehendes Debugging im Produktionseinsatz kannst du passenden Remote-React-Komponenten ausdrücklich einen Callback für den Ladeabschluss hinzufügen:

```ts
ObservabilityPlugin({
  level: 'verbose',
  react: {
    injectLoadedCallback: true,
    remoteIds: ['remote/Button'],
  },
});
```

Bei aktivierter Option versucht das Plugin, nach erfolgreichem `loadRemote` Remote-React-Funktionskomponenten zu erkennen. Es umschließt sie mit einer Komponente, die keine DOM-Knoten ergänzt. Der Wrapper fügt ausschließlich die Prop `onMFRemoteLoaded` hinzu. Er beobachtet weder React-Mounts noch den Rendering-Lifecycle oder Timeouts. Wenn der Provider `props.onMFRemoteLoaded?.()` aufruft, erfasst der Bericht `component:business-loaded`.

Wenn `summary.componentLoaded` nach dem Aktivieren von `react.injectLoadedCallback` weiterhin `false` ist, prüfe zuerst, ob der Provider-Code tatsächlich `props.onMFRemoteLoaded?.(...)` aufruft. Andernfalls kann der Bericht nur belegen, dass die Remote-Ressource geladen wurde. Er kann nicht belegen, ob die Komponente den vom Provider definierten Bereitschaftspunkt erreicht hat. Wenn du keinen Zugriff auf den Provider-Code hast, bitte das zuständige Team um Bestätigung, dass der Callback ergänzt wurde.

Diese Option ändert die Komponentenreferenz, weil `loadRemote` eine Wrapper-Komponente zurückgibt. Begrenze den betroffenen Bereich mit `remoteIds` und entferne die Option, sobald das Problem im Produktionseinsatz behoben ist.

## Mit dem Skill `mf` verwenden {#use-with-the-mf-skill}

Installiere den Skill:

```bash
npx skills add module-federation/agent-skills --skill mf -y
```

Wenn die Konsole einen Observability-Hinweis ausgibt, bitte deinen Agenten um Folgendes:

```text
/mf observability
Ich habe diesen Module-Federation-Konsolenfehler gesehen:

[Module Federation] Observability report generated
traceId: mf-...
read: window.__FEDERATION__.__OBSERVABILITY__["runtime_host"].getReport("mf-...")

Bitte lies den Bericht und behebe das Problem.
```

Unter Node oder SSR gibst du dem Agenten stattdessen den Dateipfad:

```text
/mf observability
Lies .mf/observability/latest.json und erkläre die wahrscheinliche Ursache und die Behebung.
```

Wenn deine Produktionsanwendung Berichte hochlädt, gib dem Agenten den hochgeladenen Bericht oder die `traceId`:

```text
/mf observability
Hier ist der hochgeladene Bericht für die traceId mf-...
Sag mir, ob es ein Problem von Host, Remote, Shared, Netzwerk oder Build ist.
```

## Was die KI zuerst liest {#what-the-ai-reads-first}

Der Skill liest die Felder in dieser Reihenfolge:

1. `diagnosis`
2. `summary`
3. `moduleInfo`
4. `events`

Wenn Build-Informationen benötigt werden, lies `.mf/observability/build-info.json` oder `.mf/observability/build-report.json` als separate Datei.

Berichte lassen Felder mit dem Wert `undefined` weg. Fehlt ein Feld, behandle es als nicht beobachtet oder für diesen Trace nicht relevant.
