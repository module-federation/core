{props.name || 'Module Federation'} unterstützt Node.js direkt. Ob du Module ausschließlich über die Runtime lädst oder eine Webpack-/Rspack-Build-Pipeline nutzt: Für die Integration brauchst du vergleichsweise wenig Konfiguration. Diese Seite zeigt dir die üblichen Einsatzmöglichkeiten von {props.name || 'Module Federation'} in Node.js.

## Übersicht {#overview}

In einer Node.js-Serveranwendung kannst du mit {props.name || 'Module Federation'} Remote-Module laden. Das können lokale Dateien im CommonJS-Format oder über HTTP erreichbare Remote-Dienste sein. So entsteht eine flexible Grundlage für serverseitige Microservices, dynamisch bereitgestellte Funktionen und gemeinsam genutzte Ressourcen.

## Consumer {#consumer}

### Nur mit der Runtime {#runtime-only}

Wenn du in Node.js nur Module konsumierst und keinen Bundler wie Webpack oder Rspack einführen möchtest, kannst du ausschließlich die Runtime verwenden. Dabei gilt: **Du brauchst keine Build-Plugins**. Die APIs von { props.runtime || '@module-federation/runtime' } reichen aus.

So gehst du vor:

1. **Erstelle eine MF-Instanz** mit `createInstance`.
2. **Registriere Remotes** über das Array `remotes`.
3. **Lade Module** mit `loadRemote`.

## FAQ {#faq}

### 1. Was bewirkt `target: 'async-node'`? {#1-what-does-target-async-node-do}

`target: 'async-node'` ist ein Webpack-Build-Ziel, das eine für Node.js geeignete Ausgabe mit asynchronem Laden erzeugt. Das ist für das dynamische, asynchrone Lademodell von Module Federation wichtig, insbesondere wenn du beim Laden von Remotes `await` auf oberster Ebene brauchst.

### 2. Warum muss ich `remoteType: 'script'` setzen? {#2-why-do-i-need-to-set-remotetype-script}

Die MF-Bundler-Runtime unterstützt derzeit nur den Remote-Ladetyp `script`. Deshalb musst du für die Nutzung in Node.js ausdrücklich `remoteType: 'script'` setzen.
