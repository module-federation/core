# Nuxt {#nuxt}

`@module-federation/nuxt` ist ein Nuxt-Modul, das Module Federation in Nuxt-Hosts und -Remotes integriert. Es verwendet `@module-federation/vite` mit dem standardmäßigen Vite-Builder von Nuxt oder `@module-federation/enhanced/rspack`, wenn die Anwendung den Rspack-Builder nutzt. Du konfigurierst Federation also unabhängig vom Builder einmal in `nuxt.config.ts`.

:::warning Beta
`@module-federation/nuxt` befindet sich noch in der Beta-Phase. Die API kann sich ändern, während die Integration weiterentwickelt wird. Melde Fehler und Sonderfälle bitte in [module-federation/nuxt](https://github.com/module-federation/nuxt).
:::

## Unterstützt {#supports}

- Nuxt `>=4.5.1` mit dem standardmäßigen Vite-Builder oder einer passenden Version von `@nuxt/rspack-builder`
- Node.js `^22.18.0`, `^24.11.0` oder `>=26.0.0`
- Serverseitig gerenderte Remote-Komponenten in Entwicklung und Produktion auf Node-Deployments mit Schreibzugriff
- Konventionsbasierte Komponenten-Exposes aus `~/components/exposed`
- Remote-Vue-Komponenten, die für Nuxt-Template-Auto-Imports registriert werden
- `vue` und `vue-router`, die standardmäßig als Singletons geteilt werden

## Installation {#installation}

Installiere das Modul sowohl im Host als auch im Remote:

## Remote konfigurieren {#configure-a-remote}

Registriere das Modul und gib jedem bereitgestellten Container einen eindeutigen Namen:

```ts title="nuxt.config.ts"
export default defineNuxtConfig({
  modules: ['@module-federation/nuxt'],
  moduleFederation: {
    config: {
      name: 'catalog',
    },
  },
});
```

Komponenten in `app/components/exposed` werden automatisch bereitgestellt. Beispielsweise wird `app/components/exposed/ProductCard.vue` für Hosts als `./ProductCard` bereitgestellt.

Du kannst `exposes` auch direkt konfigurieren. Relative Pfade werden vom Stammverzeichnis der Nuxt-Anwendung aus aufgelöst:

```ts title="nuxt.config.ts"
export default defineNuxtConfig({
  modules: ['@module-federation/nuxt'],
  moduleFederation: {
    config: {
      name: 'catalog',
      exposes: {
        './catalog-app': './app/app.vue',
      },
    },
  },
});
```

## Host konfigurieren {#configure-a-host}

```ts title="nuxt.config.ts"
export default defineNuxtConfig({
  modules: ['@module-federation/nuxt'],
  moduleFederation: {
    remoteComponents: {
      catalog: ['ProductCard'],
    },
    config: {
      name: 'shell',
      hostInitInjectLocation: 'entry',
      remotes: {
        catalog: {
          type: 'module',
          name: 'catalog',
          entry: 'https://catalog.example.com/mf-manifest.json',
          entryGlobalName: 'catalog',
          shareScope: 'default',
        },
      },
    },
  },
});
```

Die bereitgestellte Komponente steht anschließend über die Komponenten-Auto-Imports von Nuxt zur Verfügung:

```vue title="app/app.vue"
<template>
  <RemoteProductCard product-id="123" />
</template>
```

Bei der Einrichtung ruft das Modul die `mf-manifest.json` jedes Remotes ab und registriert dessen Komponenten-Exposes. `remoteComponents` ist die Fallback-Liste, wenn das Manifest nicht erreichbar ist, etwa wenn das Remote unabhängig vom Host-Build bereitgestellt wird.

Bevorzuge Manifest-URLs für SSR-Hosts: Die Runtime wählt anhand des Manifests den Browser- oder Server-Entry aus und kann einen neuen Server-Build erkennen, ohne den Host neu zu starten.

### Komponentennamen {#component-names}

Bei einem einzelnen Remote wird `./ProductCard` zu `RemoteProductCard`. Bei mehreren Remotes enthält der Name zur Vermeidung von Konflikten den Remote-Namen. So wird `catalog/ProductCard` zu `RemoteCatalogProductCard`.

Nur Expose-Namen, die mit einem Buchstaben beginnen und ausschließlich Buchstaben, Zahlen, Unterstriche oder Bindestriche enthalten, werden als Nuxt-Komponenten registriert. Andere Exposes sind weiterhin über gewöhnliche Runtime-Imports verfügbar.

## Serverseitiges Rendering {#server-rendering}

Remote-Komponenten werden standardmäßig auf dem Nuxt-Server gerendert. Ein produktives Remote veröffentlicht sowohl `remoteEntry.js` für den Browser als auch `remoteEntry.ssr.js` für den Server. Der Host lädt beim Rendering den Server-Entry, fügt das Remote-HTML in seine Antwort ein und hydratisiert dieselbe Komponente im Browser.

Der standardmäßige SSR-Loader schreibt abgerufene Module nach `node_modules/.ssr-cache` unterhalb des Arbeitsverzeichnisses des Servers. Deaktiviere Remote-SSR bei Deployments ohne Schreibzugriff oder bei Serverless-Deployments:

```ts title="nuxt.config.ts"
export default defineNuxtConfig({
  moduleFederation: {
    ssr: false,
    config: {
      // ...
    },
  },
});
```

Schlägt ein Remote während einer Serveranfrage fehl, rendert der Host für diese Anfrage einen leeren Fallback, damit die Seite weiterhin antwortet. Spätere Anfragen versuchen erneut, das Remote zu laden.

:::warning
Remote-SSR führt den Server-Entry des Remotes mit den Berechtigungen des Host-Prozesses aus. Konfiguriere ausschließlich vertrauenswürdige Remotes und verwende in Produktion direkte HTTPS-URLs.
:::

## Gemeinsam genutzte Abhängigkeiten {#shared-dependencies}

Wenn `config.shared` nicht gesetzt ist, werden `vue` und `vue-router` mit ihren installierten Versionen als Singletons geteilt. Gib `config.shared` an, um die Standardwerte zu überschreiben:

```ts title="nuxt.config.ts"
export default defineNuxtConfig({
  moduleFederation: {
    config: {
      shared: {
        vue: { singleton: true, requiredVersion: '^3.5.0' },
        'vue-router': { singleton: true, requiredVersion: '^5.1.0' },
        pinia: { singleton: true },
      },
    },
  },
});
```

## Rspack-Builder verwenden {#use-the-rspack-builder}

Vite ist der Standard. Um Rspack zu verwenden, installiere `@nuxt/rspack-builder` in derselben Version wie Nuxt und setze in der Anwendung `builder: 'rspack'`:

```ts title="nuxt.config.ts"
export default defineNuxtConfig({
  builder: 'rspack',
  modules: ['@module-federation/nuxt'],
  moduleFederation: {
    config: { name: 'catalog' },
  },
});
```

Beide Builder verwenden dieselbe `moduleFederation`-Konfiguration und können die Manifeste des jeweils anderen einbinden. Optionen, die nur für Vite gelten, etwa `hostInitInjectLocation`, werden von Rspack ignoriert.

## Optionen {#options}

Konfiguriere diese Werte unter `moduleFederation` in `nuxt.config.ts`:

| Option | Typ | Standardwert | Beschreibung |
| --- | --- | --- | --- |
| `base` | `string` | `"/"` | Öffentlicher Pfad und Ausgabeverzeichnis für Federation-Entries und das Manifest. |
| `exposedDir` | `string` | `"~/components/exposed"` | Verzeichnis, dessen Komponenten automatisch bereitgestellt werden. |
| `manifestFetchTimeoutMs` | `number` | `500` | Maximale Zeit beim Setup zum Abrufen jedes Remote-Manifests. |
| `manifestMetadata` | `Record<string, unknown>` | `{}` | Werte, die in generierten Manifest- und Stats-Dateien mit `metaData.custom` zusammengeführt werden. |
| `remoteComponents` | `Record<string, string[]>` | `{}` | Zu registrierende Komponenten-Exposes, wenn die Manifest-Erkennung nicht verfügbar oder deaktiviert ist. |
| `ssr` | `boolean` | `true` | Eingebundene Remote-Komponenten auf dem Nuxt-Server rendern. Server-Exposes werden auch bei `false` weiterhin veröffentlicht. |
| `ssrFetchTimeoutMs` | `number` | `10000` | Maximale Zeit für jede SSR-Remote-Netzwerkanfrage; `0` deaktiviert das Timeout. |
| `ssrManifestMaxAgeMs` | `number` | `30000` | Intervall, nach dem der Server ein Remote-Manifest erneut auf eine neue Version prüft. |
| `config` | `FederationOptions` | | Module-Federation-Optionen, die an den ausgewählten Builder übergeben werden. Siehe [Konfigurationsübersicht](/configure/index.html). |

Die [Paketreferenz](https://github.com/module-federation/nuxt/blob/main/packages/nuxt/README.md) beschreibt typisierte Remote-Komponenten, Bridge-Anwendungsexports und alle Anforderungen an das Deployment.
