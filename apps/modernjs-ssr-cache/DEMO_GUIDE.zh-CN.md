# Modern SSR Remote 更新体验指南

这份指南面向第一次体验的同事。建议按顺序操作，重点观察：真实 SSR 与水合、更新后页面版本、宿主模块是否保留、更新期间请求如何等待，以及 Host 内存变化。

## 1. 启动

需要包含 `apps/modernjs-ssr-cache` 的仓库版本。目前开发分支为 `feat/ssr-published-acceptance`，对应 [PR #5076](https://github.com/module-federation/core/pull/5076)。如果没有这个目录，请先确认代码版本；不是旧的 `apps/modernjs-ssr` demo。

使用 Node.js 24、pnpm 10.28.0。在该仓库根目录执行：

```sh
corepack enable
pnpm install --frozen-lockfile
node apps/modernjs-ssr-cache/start.cjs --memory
```

依赖已安装时，可以直接执行最后一条命令。保留仓库中的锁文件、Rspack override 和 Modern patch；本例依赖尚未正式发布的配套能力，不要自行替换成 latest。

启动脚本依次构建七个 Modern 项目，然后运行编译后的 SSR 服务。看到 `PLAYGROUND_READY` 后打开：

**<http://127.0.0.1:3059/>**

这是生产构建后的运行体验，不是开发模式 HMR。启动需要构建，但点击更新按钮只切换已经构建好的 v1/v2 产物，不重新编译、不退出 Host 进程。结束体验时，在启动终端按 Ctrl+C。

## 2. 先分清控制台、Host 和 Remote

| 对象 | 用途 |
| --- | --- |
| 控制台，端口 3059 | Modern SSR 应用，提供操作按钮、iframe、请求记录和内存图表 |
| 静态 Host | 独立 Modern SSR 消费者进程，用于体验局部更新 |
| 动态 Host | 另一个消费者进程，用于体验动态消费和整体重建 |
| Remote | Modern 构建的生产者组件，预先准备 v1/v2 版本 |

控制台不是被测 MF Host。页面里的 iframe 访问真正的 Host；两个 Host 使用自动分配的端口，重启后可能变化。

每个 Host 有两个 SSR 入口：

- **A 入口 `/`**：节拍器页面，消费名为 `remote` 的 Remote A。
- **B 入口 `/b`**：独立配色页面，作为不依赖 Remote A 的对照入口。

“A/B 入口”不是两个 remote。动态 Host 的 A 页面另外可以加载 `lab_palette` remote，UI 将它标作 Remote B；它与 `/b` 对照入口也不是同一概念。

**不要访问 `http://127.0.0.1:3059/b`，控制台没有这个路由。** 如需直接访问 Host，可在另一个终端读取当前地址：

```sh
curl -fsS http://127.0.0.1:3059/api/state | node -e 'let s="";process.stdin.on("data",d=>s+=d);process.stdin.on("end",()=>{for(const [kind,h] of Object.entries(JSON.parse(s).hosts))console.log(kind,h.url,h.url+"/b");});'
```

控制台持续请求 `/api/state` 是为了刷新状态，不会因此更新 remote，也不会自动采集内存。

## 3. 体验 SSR、缓存和水合

1. 选择「静态 Host · 局部更新」，进入「功能体验」。
2. 等待左右节拍器页面显示 `Hydrated · 可以交互`。在左侧点击 `+` 修改 BPM。
3. 点击「更新到 v2」。右侧会发起新的真实 SSR 请求并展示 v2；左侧保留旧页面及其交互状态。
4. 点击「查看真实 HTML」，检查返回 HTML 中的 `data-release="v2"`，确认新版组件已经包含在服务端响应中。
5. 点击「重新请求右侧页面」，观察同一版本下模块初始化 ID 保持不变、loader 调用计数增加。

右侧不是只在当前页面做 CSR 替换：它是新的 iframe 导航，先收到 SSR HTML，再在浏览器水合。左侧旧窗口不会因为服务端更新自动变成新版。

## 4. 区分局部更新与整体重建

每个入口显示「服务端模块状态」：

- **初始化 ID / 时间**：由入口的服务端 loader 模块在初始化时生成。
- **累计 loader 调用**：模块变量计数，包含其他窗口、预热和实验请求，不等于点击次数或成功渲染次数。
- **Host PID**：真正执行 SSR 的进程。

操作顺序：

1. 选择静态 Host，找到「B 入口：更新 A 后，宿主模块是否保留？」的左右窗口。
2. 记下 B 的初始化 ID，然后用上方「更新到 v1/v2」切换 Remote A。
3. 对比 B 的新旧 ID、计数和 PID。
4. 切换到动态 Host，等页面加载，再重复更新和对比。

| 观察项 | 静态 Host 局部更新 | 动态 Host 整体重建 |
| --- | --- | --- |
| A 初始化 ID | 改变，A 依赖被更新的 remote | 改变 |
| B 初始化 ID | 保留 | 改变 |
| B 调用计数 | 继续累计 | 随新模块重新开始累计 |
| Host PID | 不变 | 不变 |

**判断区别要看未受影响的 B，不能要求静态 Host 的 A ID 也不变。** 即使当前已经是 v2，再点「更新到 v2」仍会执行更新。普通刷新不触发更新，但刷新控制台会重新建立左侧对比基准；此前更新留下的旧页面也会被替换。

这里展示的是入口级更新，不是任意子路由都能独立更新。整体重建也不是重启 Node：它重建 SSR 应用资源，不会自动清除业务写入 `globalThis` 的值、监听器或后台任务。

## 5. 体验动态 remote

1. 选择动态 Host，在 A 页面的「浏览器动态加载」区域点击「＋ 加载配色面板」。这是浏览器中动态注册并加载 remote。
2. 点击控制台的「注册动态 Remote 并 SSR」。
3. 等新页面完成加载，点击「查看真实 HTML」，确认响应中包含 `Choose a mood.`。

第二步让后续 A 页面的 SSR 包含动态 remote。动态 Host 明确使用整体重建模式，不把运行时曾经加载过的 remote 记录当成完整静态依赖图。

## 6. 看更新期间请求如何等待

在「让请求撞上更新。」中，建议先使用默认「排队后自动恢复」：

1. 点击「开始并发实验」。它会自动扣住一个旧 loader、触发 remote 更新，然后发送新请求，无需另外点更新按钮。
2. 观察 A1、A2、A3、B1 四个真实 iframe。
3. 静态 Host 更新时，三个 A 窗口等待，B 可以正常返回；动态 Host 整体重建时，四个窗口都需要等待。
4. 默认约 1.4 秒后自动释放旧请求，更新完成，等待的页面返回并水合。

默认还有 **12 条 Node HTTP 请求：9 条 A、3 条 B**。这不是组件数量；四个 iframe 是额外的四次浏览器请求。因此 Node 结果列表不等于全部浏览器请求，实际排队数会包含 iframe。

想手动观察可选择「手动释放」，开始实验后及时点击「释放旧请求」。当前排队超时为 **3 秒**，超过后可能得到真实 503；手动模式不会取消超时限制。「队列满 503」「等待超时 503」就是故意制造失败的测试模式。

保持实验页在前台。页面没有赶上等待阶段会报告失败；错误响应会保留展示，不会伪造成功页面或自动降级成旧页面。

## 7. 观察内存

进入「内存观察」，先确认当前选择的是哪个 Host。所有样本来自该 Host 进程的 `process.memoryUsage()`，包含 Modern、宿主、服务端 remote 和相关缓存；不包含控制台、浏览器或流量发生器，也不是 remote 文件体积。

手动比较：

1. 点击「GC 后采样」，记录基准。
2. 点击「更新 remote 到 v1/v2」，等待下方「手动更新的真实页面」展示新版本。
3. 再点击「GC 后采样」，比较表格的 Heap 和 RSS。
4. 可以重复几次，观察趋势。普通「采样一次」只记录内存，不触发更新或显式 GC。

「GC 后采样」会同步调用 GC、让出一次事件循环、再同步 GC，然后读取内存。它不保证所有异步清理都结束，也不保证内存一定下降：仍被引用的对象不会释放，回收后的空间也不一定马上归还操作系统。

| 指标 | 如何理解 |
| --- | --- |
| Heap MiB | JS 堆已使用内存；折线图画的是这个值 |
| RSS MiB | 整个 Host 进程驻留内存，可能在 Heap 稳定时仍增加 |
| 实例 | MF 全局记录中的 runtime 实例数，不是内存大小 |

点击「运行 20 次更新」会逐轮切换 v2/v1。每轮更新后发送 8 条 Node SSR 请求，再让 iframe 发起一次真实导航；收到加载确认并展示至少 0.8 秒后进入下一轮。第 5、10、15、20 轮 GC 后采样，共四次。页面保留 20 轮记录；15 秒未收到页面加载确认会报告失败。保持内存页打开。

不要只凭一次内存涨跌判断泄漏或更新范围。应比较相同实验条件下多轮 GC 后的趋势，结合模块状态和必要的堆快照分析。

## 8. 手动调试和自动验证

如需调试，先退出正在运行的 demo，再启动：

```sh
node apps/modernjs-ssr-cache/start.cjs --debug
```

在 Chrome 打开 `chrome://inspect`，连接静态 Host 的 9230 或动态 Host 的 9231。此模式也开启显式 GC。「生成堆快照」按钮会返回快照文件路径，可在 DevTools Memory 中加载分析。

自动 E2E 从仓库根目录运行：

```sh
node apps/modernjs-ssr-cache/e2e.cjs
```

它启动独立测试服务，运行 Cypress 浏览器场景和真实 HTTP 检查，结束后关闭测试服务。**运行前先停止同一 checkout 中的体验服务**：两者会重建同一组 `dist` 和 `releases`，同时运行会互相覆盖产物。结束后重新执行体验启动命令即可。

脚本职责、版本限制和实现细节见 [README](./README.md)。当前仍使用 Modern 预览包的 SSR patch，Host 服务端 splitChunks 被关闭；本 demo 不能证明这些限制已解决，也不能直接当成生产管理接口部署。
