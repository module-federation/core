Rstest Compatibility Report: Vitest Migration Friction

This report documents the non-mechanical parts of migrating module-federation/core package tests from Vitest to Rstest. It intentionally excludes straightforward API renames such as vi.fn() to rs.fn() and direct config field moves from vitest.config.* to rstest.config.*.

Report date 2026-07-06
Repository module-federation/core
Runtime Node.js 20.19.5, pnpm 10.28.0
Test runners Vitest 1.6.0 -> Rstest 0.10.6

Migration Outcome

The migrated package test suite is passing after the workarounds described below. A comparable Turbo benchmark across the originally Vitest-backed package set showed Rstest faster after migration:

Runner Samples Average wall time Average Turbo time
Vitest 14.92s, 14.27s, 14.19s 14.46s 14.164s
Rstest 12.71s, 12.30s, 12.09s 12.37s 11.852s

The performance result is positive, but the migration still required manual behavior rewrites in several areas where Vitest projects could not be replaced seamlessly.

Compatibility Findings

1. Fetch mocking did not have a drop-in replacement

High

A shared static-server helper used vitest-fetch-mock to intercept local fixture requests. The migration could not be expressed as an API rename and required reimplementing fetch routing manually with web platform Request and Response objects.

Files packages/runtime/__tests__/mock/utils.ts
packages/runtime-core/__tests__/mock/utils.ts
Original Vitest pattern 
const fetchMocker = createFetchMock(vi);
fetchMocker.enableMocks();
fetchMocker.doMock();
fetchMocker.mockIf(match, (req) => {
  return { url: req.url, body, headers };
});
Rstest workaround 
const nativeFetch = globalThis.fetch?.bind(globalThis);

rs.stubGlobal(
  'fetch',
  rs.fn(async (input, init) => {
    const req = input instanceof Request ? input : new Request(input, init);
    if (!match(req)) return nativeFetch(req);
    return new Response(body, { headers });
  }),
);

Desired improvement: provide an official fetch mocking helper, a Vitest-compatible adapter, or migration documentation that covers enableMocks(), doMock(), and mockIf(predicate, handler). The compatibility layer should preserve native fetch fallback behavior and make it obvious how handlers should return status, headers, body, and delayed responses.

2. Auto-mock and manual mock resolution differed from Vitest

High

Several Vitest tests relied on factory-less module mocks. Under Rstest these mocks either looked for manual mock files that did not exist or did not expose the mocked function shape expected by the test. The fix was to replace terse mocks with explicit factories and hoisted mock state.

Files packages/dts-plugin/src/core/lib/DTSManager.general.spec.ts
packages/dts-plugin/src/core/lib/consumeTypes.spec.ts
Observed symptoms 
Error: Cannot find module '.../packages/dts-plugin/__mocks__/fs/promises'
Error: Cannot find module './__mocks__/utils'
Error: Cannot find module './__mocks__/archiveHandler'
Original Vitest pattern 
vi.mock('fs/promises');
vi.mock('fs');
vi.mock('./archiveHandler');
vi.mock('./utils');
Rstest workaround 
const fsPromisesMocks = rs.hoisted(() => ({
  cp: rs.fn().mockResolvedValue(undefined),
  mkdir: rs.fn().mockResolvedValue(undefined),
  rm: rs.fn().mockResolvedValue(undefined),
}));

rs.mock('fs/promises', () => fsPromisesMocks);
rs.mock('./utils', () => ({
  getDTSManagerConstructor: rs.fn(),
}));

Desired improvement: document the exact mock resolution model relative to Vitest, improve the error message when Rstest is looking for __mocks__, and consider an automock compatibility mode for common vi.mock('module') migrations.

3. Parameterized snapshot names were not compatible

High

Existing snapshots generated by Vitest for parameterized tests did not match the snapshot keys Rstest looked up. The affected tests used it.each(...) with a title containing %p. Instead of simply accepting the old snapshot file, the migration had to remove those snapshot assertions and replace them with structural toEqual assertions.

Files packages/dts-plugin/src/core/rpc/wrap-rpc.spec.ts
packages/dts-plugin/src/core/rpc/__snapshots__/wrap-rpc.spec.ts.snap
Vitest snapshot key shape 
exports[`wrapRpc > once > rejects on process close with %p { code: -1, signal: undefined, ... } 1`] = ...
Rstest workaround 
expect(eventHandlers['close']).toEqual([expect.any(Function)]);
...
expect(eventHandlers).toEqual({
  message: [],
  close: [],
});

Desired improvement: offer a snapshot migration command or compatibility mode that can rewrite Vitest snapshot keys to Rstest keys, especially for it.each titles using format placeholders such as %p. If key compatibility is not intended, the failure output should point to a documented migration path.

4. Type-level assertions lost an equivalent API

Medium

Vitest's expectTypeOf was used for generic public API checks. Rstest did not expose a direct equivalent, so the migration replaced those assertions with assignment-based TypeScript checks. This preserved positive compatibility checks but lost the readable assertion style and the negative assertions.

File packages/runtime/__tests__/global.spec.ts
Original Vitest pattern 
expectTypeOf(typedLoadRemote).returns.toMatchTypeOf<
  Promise<string | null>
>();

expectTypeOf(typedLoadRemote).returns.not.toMatchTypeOf<Promise<null>>();
Rstest workaround 
type LoadRemoteReturn = ReturnType<typeof typedLoadRemote>;
const _acceptsStringOrNull: Promise<string | null> =
  null as never as LoadRemoteReturn;
void _acceptsStringOrNull;

Desired improvement: export an expectTypeOf-compatible API from Rstest or document the recommended companion package and setup. Ideally this should cover negative assertions too, because those are common when testing generic API surfaces.

5. Async matcher behavior required source edits

Medium

Tests that used unawaited expect(promise).resolves and expect(promise).rejects emitted warnings under Rstest and had to be changed to await expect(...). This is a reasonable correctness improvement, but it is still a migration edit outside API/config mapping.

File packages/dts-plugin/src/core/rpc/wrap-rpc.spec.ts
Original pattern 
expect(promise).resolves.toEqual(41);
expect(wrapped()).rejects.toEqual(new Error('cannot send'));
Rstest-compatible pattern 
await expect(promise).resolves.toEqual(41);
await expect(wrapped()).rejects.toEqual(new Error('cannot send'));

Desired improvement: provide a codemod or migration lint for awaiting promise matchers. Also update warning text so it does not read as a Vitest runtime message when emitted during an Rstest run.

6. Vite framework plugins needed Rsbuild-specific replacements

Medium

Rstest runs through Rsbuild/Rspack, so framework plugin migration was not just moving config fields. React and Vue JSX tests required explicit Rsbuild plugin choices. Vue JSX was especially surprising: without the Vue JSX plugin path, TSX compilation failed with React default assumptions.

Files packages/bridge/bridge-react/rstest.config.ts
packages/bridge/vue3-bridge/rstest.config.ts
React replacement 
import { pluginReact } from '@rsbuild/plugin-react';

export default defineConfig({
  plugins: [pluginReact()],
});
Vue JSX replacement 
import { pluginBabel } from '@rsbuild/plugin-babel';
import { pluginVueJsx } from '@rsbuild/plugin-vue-jsx';

export default defineConfig({
  plugins: [
    pluginBabel({ include: /\.(?:jsx|tsx)$/ }),
    pluginVueJsx(),
  ],
});

Desired improvement: add a Vite-to-Rsbuild plugin replacement matrix to Rstest migration docs. Useful entries for this migration: @vitejs/plugin-react to @rsbuild/plugin-react, and @vitejs/plugin-vue-jsx to @rsbuild/plugin-vue-jsx with any required Babel settings. Diagnostics for TSX compilation should mention Vue JSX when Vue dependencies or Vue files are present.

7. Mixed Jest and Vitest packages need migration guidance

Low

One package had a Vitest config and Vitest-style test file, but its package test script executed Jest only. To keep both existing Jest coverage and the migrated Rstest spec, the package script had to be split into two runner-specific scripts.

File packages/bridge/bridge-react/package.json
Original script 
"test": "pnpm exec jest --config jest.config.ts --passWithNoTests"
Migrated script 
"test": "pnpm run test:jest && pnpm run test:rstest",
"test:jest": "pnpm exec jest --config jest.config.ts --passWithNoTests",
"test:rstest": "pnpm exec rstest --passWithNoTests --config rstest.config.ts"

Desired improvement: document how to handle projects that have Jest and Vitest side by side. A migration planner could flag configs that are not referenced by package scripts, instead of assuming the package has exactly one active test runner.

Dependency and Ecosystem Notes

Using the latest available Rstest required raising @rstest/core from ^0.8.0 to ^0.10.6. Framework replacement plugins added during the migration were @rsbuild/plugin-react@2.1.0, @rsbuild/plugin-babel@2.0.1, and @rsbuild/plugin-vue-jsx@2.0.1. The root Vitest dependency remains because non-package app tests still use it, but unused package-test dependencies such as vitest-fetch-mock, @vitest/coverage-v8, @vitest/coverage-istanbul, and @vitest/ui were removed.

Desired improvement: make version and peer dependency selection part of the official migration guide, especially for Rsbuild 2 plugin compatibility and the Node.js requirement of current Rstest releases.

Validation Pointers

Build validation is separate from this compatibility report. The package test migration passed, while a full package build exposed an existing React type incompatibility in packages/bridge/bridge-react/src/router/default.tsx and packages/bridge/bridge-react/src/router/v6.tsx that is unrelated to Rstest execution.
